# 0.15.31 补点关闭值同步修正

日期：2026-11-06（Asia/Shanghai）。版本：0.15.31 / 63。本地长期签名正式版，作用域保持系统与传送门。

## 问题与证据

用户确认在关闭补点并重启后才进行测试。`LSPosed_20261106_082242.zip` 当前 0.15.30/62 段显示 07:23:46、07:23:57、07:24:08、07:24:44 共 4 轮实际补点；08:22 仍有候选准备。结合用户确认，这属于关闭后仍执行的异常。脱敏记录见 `artifacts/tap-switch-summary-20261106-082242.md`，日志 SHA-256 为 `691B656ABF4E4DB0AEE73CABDEAF7CCE6103D0473A33D522A3915B0ED8230569`。

本地关闭值能持久保存为明确的 Boolean.FALSE，快照序列化也保留 false。对已交付 APK 的 R8 代码核对确认补点门控未被移除。归档主数据库缺少 WAL，并且模块 APK 路径落后于文本 dump，不能把其中历史 build60 配置当作测试时的实时状态。

本轮复现了实际发布漏洞：libxposed 102 RemotePreferences.commit 先更新进程缓存，再提交框架；远程失败不回滚缓存。原 RuntimePublisher.store 把本地缓存相等当作已写入，下一次同步可能跳过实际提交，使系统继续保留旧值。本日志没有保存对应提交失败记录，所以不能断言它是本次唯一原因。

## 修正

- 每次明确同步均提交完整快照，取消基于远程首选项本地缓存相等而跳过提交的优化。
- 手势保存后立即进入原单线程发布队列；generation 取消过期任务，失败时按 250/500/1000/2000/4000ms 有限重试。耗尽后明确提示手动重试。
- 框架断连/重连回调串行处理，避免旧连接死亡通知清掉新连接。所有远程写入仍在后台，不在 UI 主线程等待 Binder。
- 手势页直接显示系统生效状态；本体已保存、框架已保存及系统 identity 确认分别处理。只有系统回报匹配身份及能力，才显示“系统已确认配置”。
- 新增固定 `runtime config` 的 stored/loaded/confirmed 诊断，记录 build 与 supplemental_tap=on/off；日志分析器严格过滤来源、日期与字段，不保留正文、URL、nonce 或 identity。

## 验证与限制

最终 44 套定向 Java/Kotlin 测试共 652 项，0 失败、错误或跳过；56 项日志工具测试通过。新增测试使用真实 libxposed RemotePreferences 编辑器与模拟框架 Binder，覆盖缓存前移失败、重试真实写入、立即排队、旧开启任务被新关闭取代、断线重连、重试耗尽及 identity 未匹配不误报确认。另有 false 冷读、UI 状态及固定诊断测试。关键旧实现缺口先失败再通过。

没有新增常驻服务或启动广播。若模块进程在系统确认前被终止，发布仍可能未完成；系统重启本身不代表本体配置已同步。因此需要以页面“系统已确认配置”作为新值已到达系统端的反馈，不宣称跨进程瞬时原子保存。
